Great question! Short answer: I would not add a separate index on `status` alone, because with only three distinct values (pending, paid, refunded) and roughly 92% of the 14 million rows being `paid`, Postgres will almost always prefer a sequential scan for `status = 'paid'` anyway, and the index would just cost you write throughput on every insert. What you actually want depends on the query. Your slow query filters on `customer_id` and `status` and sorts by `created_at DESC` with a `LIMIT 20`, so a composite index on `(customer_id, status, created_at DESC)` lets Postgres jump straight to the customer, filter the status inside the index, and read the first 20 rows already in order, which in my experience takes queries like this from a few hundred milliseconds down to single-digit milliseconds. If most of your lookups are for `pending` orders specifically, a partial index is even better: `CREATE INDEX CONCURRENTLY orders_pending_idx ON orders (customer_id, created_at DESC) WHERE status = 'pending';` is much smaller (it only covers the ~3% of rows that are pending) and stays hot in memory. One caveat: partial indexes are only used when the query's WHERE clause matches the index predicate exactly, so if your ORM parameterizes the status value as `$2`, the planner can't prove the predicate and will skip it — you'd need to inline the literal. Also make sure to use CONCURRENTLY on a table this size, otherwise the build takes an ACCESS EXCLUSIVE-ish lock (actually a SHARE lock, which blocks writes) for the whole build, which on 14M rows could be several minutes. After creating it, run `EXPLAIN (ANALYZE, BUFFERS)` on the real query and confirm you see an Index Scan on the new index rather than a Bitmap Heap Scan or Seq Scan. Hope this helps!
